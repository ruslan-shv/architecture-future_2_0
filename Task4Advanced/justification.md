# Обоснование событийного подхода vs Camel + DWH

## Проблемы текущей модели (AS-IS)

1. **DWH как интеграционная шина** — бизнес-логика и ETL смешаны; любое новое направление увеличивает нагрузку на SQL Server 2008.
2. **Синхронные маршруты Camel** — жёсткая связность; каскадные сбои при недоступности DWH.
3. **Time-to-market** — отчёты строятся часами из-за цепочки трансформаций.
4. **Масштабирование** — сотни ТБ и новые домены (фарма, оборудование) не масштабируют монолитный DWH линейно.

## Преимущества Event-Driven Architecture

| Критерий | Camel + DWH | События + домены |
|----------|-------------|------------------|
| Связность | Высокая | Низкая (pub/sub) |
| Масштабирование | Вертикальное на DWH | Горизонтальное по доменам и топикам |
| Скорость реакции | Batch, часы | Near-real-time витрины |
| PHI в аналитике | Риск утечки через общий DWH | Контракты без мед. полей |
| Новый домен | Переписывание ETL | Подписка на Published Language |

## Роль Camel и DWH при миграции

- **Anti-Corruption Layer** — адаптеры переводят legacy-сообщения в канонические события.
- **DWH** — read replica / CDC источник до полного вывода; не центр логики.
- **Срок** — dual-write ограничен этапами 1–2 (6–18 мес.) по roadmap.

## Вывод

Событийная платформа соответствует цели «слабосвязанная событийная архитектура через 3 года» и позволяет развивать медицину, финтех и ИИ независимо, сохраняя целостные KPI через Analytics domain без PHI.
